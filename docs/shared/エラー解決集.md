## MIUI（Xiaomi端末）の強制ダークモードによる起動時クラッシュ

- 発生日: 2026-07-16
- 対象プロジェクト: ラブ万歩計
- 環境: Xiaomi / MIUI端末（強制ダークモード機能が有効な端末全般）
- エラーメッセージ: `Resources$NotFoundException`（Resource ID #0x0）
- 発生した操作: アプリ起動直後（テーマ適用〜最初の画面描画のタイミング）
- 原因: MIUIの「強制ダークモード」機能が、アプリの画像リソースをダーク用に
  変換しようとして失敗し、存在しないリソースIDを参照してクラッシュする。
  アプリ側でダークモード対応を意図していなくても、MIUI側が強制的に変換処理を
  かけてくるために発生する。
- 試したこと: （このプロジェクトでは最初から `forceDarkAllowed` 対応で解決）
- 最終的な解決方法: `res/values/themes.xml` のテーマに
  `<item name="android:forceDarkAllowed">false</item>` を追加し、
  MIUIの強制ダークモード変換の対象から外す。
  ```xml
  <style name="Theme.アプリ名" parent="android:Theme.Material.Light.NoActionBar">
      <item name="android:forceDarkAllowed">false</item>
  </style>
  ```
- 他のプロジェクトでも使える知識: Xiaomi/MIUI端末（一部OPPO/vivo等の中国メーカー系ROMも同様の機能を持つ）をターゲットにする場合、
  ダークモード非対応・非対応を明示したいアプリでは `forceDarkAllowed=false` を
  テーマに入れておくと起動時クラッシュを未然に防げる。実機がなくても
  レビューで見落としやすいポイントなので、新規Androidアプリのテーマ定義時に
  最初からチェック項目に入れておくとよい。
- 関連ファイル: `app/src/main/res/values/themes.xml`

## フォアグラウンドサービスがタスクキル後に停止する（設計上の対策）

- 発生日: （ラブ万歩計では設計時から対策済みのため、実際のクラッシュ発生日は
  特定できず。今後同種の問題が実際に発生したら日付を追記する）
- 対象プロジェクト: ラブ万歩計
- 環境: Android 一般（タスクキル・メモリ回収が積極的な端末、MIUI/OPPO/vivo等で特に顕著）
- エラーメッセージ: （クラッシュではなく、バックグラウンドでの計測が止まる）
- 発生した操作: アプリをタスク一覧からスワイプで削除する
- 原因: `onTaskRemoved()` が呼ばれてもサービスが自動再起動されるとは限らず、
  メーカー独自の電力管理機能によりプロセスごと終了させられることがある。
- 試したこと:
  - `stopWithTask="false"` をサービス定義に指定
  - `START_STICKY` を返す
- 最終的な解決方法:
  - `onTaskRemoved()` 内で `AlarmManager` を使い1秒後にサービスを再起動する
    `PendingIntent` をセットする
  - `WorkManager`（`StepSyncWorker`）で定期的にサービスの生存確認と再起動を行う
    二重の保険をかける
- 他のプロジェクトでも使える知識: バックグラウンドで動き続ける必要がある
  Androidサービスは、`onTaskRemoved` + `AlarmManager` による即時再起動と、
  `WorkManager` による定期的な生存確認・再起動を組み合わせる「二段構え」が
  有効。メーカー独自のバッテリー最適化（MIUI/OPPO ColorOS/vivo FuntouchOS等）は
  OS標準の仕組みだけでは対処しきれないため、ユーザーにバッテリー最適化除外を
  案内するダイアログも合わせて用意すると良い。
- 関連ファイル:
  `app/src/main/java/com/example/lovemanpo/StepCounterService.kt`,
  `app/src/main/java/com/example/lovemanpo/StepSyncWorker.kt`

## Compose の painterResource() がリソースID解決に失敗してクラッシュする

- 発生日: 2026-07-16
- 対象プロジェクト: ラブ万歩計
- 環境: 実機（特定端末で `painterResource()` によるリソースID解決が失敗する。
  機種非依存で起こりうる問題）
- エラーメッセージ: `Resources$NotFoundException`（Resource ID #0x0）
- 発生した操作: 画面表示時（背景画像などのCompose描画）
- 原因: Compose の `Image(painter = painterResource(id = ...))` が、
  端末上でリソースID解決に失敗してクラッシュすることがある。原因の切り分けが
  難しく、このプロジェクトでは最初BGM（`MediaPlayer`）を誤って疑い、
  BGMを完全無効化しても同じ場所でクラッシュすることを確認して初めて
  画像読み込み側が原因と判明した。
- 試したこと: 疑わしい別機能（BGM）の例外保護・無効化・遅延読み込み化を
  順に試したが解消せず、無関係と判明。
- 最終的な解決方法: 該当画像の読み込みを `painterResource()` から
  `BitmapFactory.decodeResource(context.resources, resId)` による直接デコードに
  変更し、`asImageBitmap()` でComposeに渡す。失敗時は `try/catch` で `null` を
  返しフォールバック表示にする。
  ```kotlin
  val bitmap = remember(resId) {
      try {
          BitmapFactory.decodeResource(context.resources, resId)?.asImageBitmap()
      } catch (e: Exception) {
          null
      }
  }
  ```
- 他のプロジェクトでも使える知識: 特定の画像・特定端末でだけcrashが起きて
  原因が絞り込めない場合、Composeのリソース系API（`painterResource`）を
  疑う前に他の機能を先に切り分けてしまうと時間を浪費しやすい。
  クラッシュ発生箇所（スタックトレース）に近いコードから優先して疑い、
  `painterResource()` 由来と判明したら `BitmapFactory.decodeResource()` への
  切り替えという、より低レベルで確実なAPIへのフォールバックが有効。
- 関連ファイル: `app/src/main/java/com/example/lovemanpo/MainActivity.kt`
  （`HomeScreenContent` 周辺）

## AIエージェントによるコード編集で無関係な文字が混入しコンパイルエラーになる

- 発生日: 2026-07-13
- 対象プロジェクト: ラブ万歩計
- 環境: 開発環境全般（AIエージェントにコード編集を任せているプロジェクト）
- エラーメッセージ: コンパイルエラー（構文エラー）
- 発生した操作: AIエージェントによるComposable関数の編集
- 原因: 編集時に `Box(g` のような余分な文字が誤って混入していた。
- 試したこと: （誤字を目視で特定し直接修正）
- 最終的な解決方法: 混入した誤字を削除してビルドが通ることを確認。
- 他のプロジェクトでも使える知識: AIエージェントによる自動編集は、まれに
  無関係な文字列の混入や編集の競合でコンパイルエラーを起こすことがある。
  編集直後に必ずビルド（またはコンパイルチェック）を実行してからコミットする
  運用にしておくと早期発見できる。
- 関連ファイル: （プロジェクトごとの該当ファイル）
