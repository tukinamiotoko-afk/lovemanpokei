## セキュリティ・安全性に関する懸念

- **クライアントに埋め込まれた固定の共有シークレット**: AIチャットのプロキシ
  （Cloudflare Workers）への認証に、アプリのソースコードに直書きされた
  固定文字列をHTTPヘッダーに載せるだけの簡易認証を使っている
  （`callGeminiApi()` 内、`MainActivity.kt`）。APKを解析すればこの文字列を
  誰でも取得でき、プロキシに任意のリクエストを送れてしまう可能性がある。
  ※ このファイルには実際の値は記載しない。対応するなら、
  「端末ごとに発行するトークン」「署名付きリクエスト」など、より安全な
  認証方式への切り替えを検討する。
- **デバッグメニューが本番ビルドでも常時アクセス可能**: ホーム画面の
  デバッグアイコンに `BuildConfig.DEBUG` 等のガードが一切なく、誰でも
  歩数追加・ラブレベル操作・全データ初期化などのチート的な操作に
  到達できてしまう。リリースする場合は本番ビルドから除外するか、
  隠しコマンド等でアクセス制限すべき。

## データ整合性・実装の粗さ

- **「全データ初期化」がRoomの歩数データを消さない**:
  `StepRepository.resetAllData()` は `prefs.edit { clear() }` のみを行い、
  Room側の `steps` / `hourly_steps` テーブルは対象外。ユーザーが
  「全データを初期化する」ボタンを押しても歩数履歴が一部残る可能性がある。
- **`HybridStepTracker` と `StepCounterService` のセンサー処理が重複**:
  `HybridStepTracker.kt` は独立したクラスとして加速度センサーへの
  フォールバック付き歩数検出ロジックを持つが、実際の永続記録は
  `StepCounterService` が独自にセンサー登録して行っている。
  両者の役割分担・実際の呼び出し元の整理が必要（`HybridStepTracker` が
  現状どこから使われているか要確認）。
- **Room の `AppDatabase` が `fallbackToDestructiveMigration()` のまま**:
  正式なマイグレーション定義がなく、スキーマを変更すると既存データが
  消える。歩数データ以外は`SharedPreferences`側にあるため実害は限定的だが、
  リリース後にスキーマを変える場合は要注意。
- **`Geocoder.getFromLocation`（同期・非推奨API）を使用**:
  天気の地名表示で `@Suppress("DEPRECATION")` 付きの非推奨APIを使用している。
  将来的に非同期版（`getFromLocation` のコールバック版）への置き換えを
  検討する必要がある。
- **性別を男性/女性の2択のみで扱っている箇所がある**: 歩幅計算式や
  日記画面のフォント選択などに、性別による分岐がハードコードされている。
